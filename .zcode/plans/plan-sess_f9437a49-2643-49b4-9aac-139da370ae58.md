# Turn Ridhzo's AI into a sales assistant

## What I found first (this reshapes the request)

Your spec asks for ~17 next-action types. The codebase has **two disconnected vocabularies** for "what should I do with this lead", and the lead page renders both at once:

- `RecommendedActionType` — 10 values, rule-based (`NextBestActionService`), rendered with one-tap buttons in `NbaActions.tsx`
- `NextStepKind` — 6 values, AI-produced (`leadPlan.ts:9`), rendered in `AiLeadSuggestions.tsx`

So today a rep opening a lead sees two competing "next best action" panels with different vocabularies and different buttons, and the AI's richer reasoning sits underneath the rule's, not instead of it. **The single highest-leverage change is unifying those into one `NextAction` type emitted by both.** Most of §2, §3, §7, §10 and §13 fall out of that one type rather than needing separate work.

Three other findings that shape the plan:

1. **The execution gap is 2 clicks, not a missing feature.** "Use this message" already prefills the composer via the `leadEvents` bus — but `applyAiSuggestion` never touches `next.message`, so the AI's message is transient client state, lost on refresh. Meanwhile the assistant's "Approve & send" *does* send, irreversibly, with a hardcoded email subject. The two halves of the loop already exist separately; they need joining.
2. **There is no way to measure AI quality today.** No eval set, no temperature set anywhere, recap uses prose-asked JSON + regex extraction + a costly 3000-token retry, and `AI_AGENT_MODEL` is unset so the tool-calling agent runs on a small model behind a fallback that hides it. "Improved AI results" is currently unfalsifiable — so measurement goes first.
3. **Four disagreeing inactivity thresholds** (NBA 5d, engagement tiers 3/7/14, stale 14d, org `slaHours`). The AI inherits this incoherence — it would tell a rep a lead is "going cold" while the engagement card says "healthy".

## Credit policy (the call I'm making, stated explicitly)

- **Metered** — anything a rep pressed: recap refresh, draft, assistant turn. Unchanged.
- **Free** — everything proactive: prewarm (already done), daily-summary narrative, urgency alerts, priority ranking.

Same reasoning you already accepted for prewarm: warming something the rep hasn't asked for is our cost, not theirs. Alerts are additionally urgency-gated, confidence-gated, and deduped so volume is bounded regardless.

## Phase 0 — Foundation: make AI quality measurable

Nothing after this is verifiable without it.

**0.1 Schema-enforced output.** Replace the prose-asked-JSON + `extractJson` regex + 3000-token retry in `leadAssist.ts` with `generateObject` + a Zod schema mirroring `LeadPlan`. AI SDK v7.0.89 exports both; neither is used yet. This removes the `BROKEN_RECAP` retry cost and the parse-failure class entirely.

**0.2 Set `temperature`.** Unset today, so the gateway default (typically 1.0) applies to structured extraction — wrong for this job. Set 0.2–0.3 in `src/lib/ai/client.ts`.

**0.3 Set `AI_AGENT_MODEL`** to a tool-capable free-tier gateway model, documented in `.env.example`. Today `agent.ts` silently runs on `inclusionai/ling-3.1-flash` and its non-tooling fallback masks the failure.

**0.4 Golden-set eval harness** — `src/lib/ai/__eval__/`:
- ~12 fixture leads as JSON snapshots, including adversarial ones: lead-authored note containing `<lead_data>`, zero-activity lead, admin-only-field lead, won/lost lead, cold lead, hot content-opener
- Scorer: JSON parse rate, suggestion-validity rate, field precision vs. labelled expectations, hallucinated-key rate, agreement with the rule NBA
- `pnpm eval:ai` prints a scorecard. **I record the baseline before touching anything**, and every later phase must not regress it.

## Phase 1 — The unified `NextAction` spine

**1.1 New shared type** — `src/domains/leads/nextAction.ts`:

```ts
export type NextActionKind =
  | "call" | "whatsapp" | "email" | "meeting" | "follow_up" | "wait"
  | "share_document" | "enroll_sequence" | "stop_sequence"
  | "change_status" | "assign" | "escalate"
  | "log_meeting_outcome" | "confirm_meeting" | "ask_for_info"
  | "qualify" | "mark_qualified" | "mark_unqualified" | "do_nothing";

export interface NextAction {
  id: string;                       // stable hash, so dismissals stick
  kind: NextActionKind;
  title: string;                    // ≤100 chars, imperative
  reason: string;                   // ≤240 chars, must cite a concrete fact
  evidence: string[];               // quotes backing it        → §10
  urgency: "now" | "today" | "this_week";                       → §7
  confidence: "high" | "medium" | "low";                        → §11
  message?: string;                 // ready-to-send for whatsapp/email
  followUpAt?: string;
  source: "rule" | "ai";            // provenance, shown in the UI
}
```

I picked the 19 kinds that map onto services that already exist and are already callable — spec items that were really the same action are merged rather than double-listed.

**1.2 Widen the rule engine.** `NextBestActionService.getRecommendation()` returns `NextAction` with `source: "rule"`, mapping its existing 10 actions onto the new kinds. This is the migration's real cost: five call sites read the old shape (`LeadsTable.tsx:561`, `PriorityActions.tsx:45`, `leads/profile.ts:173`, `leadBrief.ts:151`, `leads/[id]/page.tsx:279`) plus `LeadInsightsCard`. All mechanical. Existing tests keep their meaning.

**1.3 AI emits the full vocabulary.** `LeadPlan.next` becomes `NextAction | null`; `briefFormatInstructions` teaches the new kinds. `validateNextAction` enforces three deterministic rules the prompt cannot be trusted for:

- **Impossibility** — no phone for `call`, no sequence to `enroll_sequence`, status already at target → drop it.
- **Activity-awareness (§13)** — compute the rule NBA for the same lead first. If the rule says `wait` because a follow-up is already planned, or says the rep contacted this lead minutes ago, the AI's contacting action is **downgraded to `this_week` with a reason clause**, not silently trusted. This is a validator, not a prompt instruction, which is the reliable place for it.
- **Confidence gate (§11)** — `low` confidence downgrades urgency and is surfaced as advisory, not as a primary button.

**1.4 Consolidate inactivity thresholds** into `src/lib/leads/inactivity.ts` with named thresholds, replacing the 5d/3-7-14/14d/`slaHours` spread. Small, and it stops the AI contradicting the engagement card.

**1.5 Surface `bestContactWindow`** (`leads/profile.ts:157`, already derived from when the lead actually replies) into `NextAction.reason` and into `followUpAt` selection → §14, mostly already computed, currently never used for this.

## Phase 2 — Close the one-click loop

**2.1 Persist the message.** The plan is already stored in `customData._aiRecap.plan`; `applyAiSuggestion` simply ignores `next.message`. The whole `NextAction` round-trips once this is fixed, so the AI's message survives refresh.

**2.2 New `src/lib/actions/aiActions.ts` — `executeAiActionAction({ leadId, id, confirm })`.** Dispatches on `kind` to the **already-existing** server actions: `sendWhatsAppAction`, `sendEmailAction`, `createFollowUpAction`, `createMeetingAction`, `enrollLeadsAction`, `setMeetingOutcomeAction`, `assignLeadAction`, `changeLeadStatusAction`, `createShareLinkAction`. Reuses RBAC, org scoping, audit and billing gates for free — the same pattern `agent.ts` already uses. Honours the personal-vs-BSP WhatsApp branch from `WhatsAppSendBox.tsx:64`.

**2.3 One `NextActionCard` replaces `NbaActions` + the AI next-step block.** Renders evidence quotes, reason, confidence chip, urgency, the message preview, and buttons per kind: **Send** (confirm dialog — outbound is irreversible), **Use & edit**, **Copy**, **Schedule**, **Dismiss**. `wait`/`do_nothing` renders *"Nothing to do until {date}"* instead of today's zero-button blank.

**2.4 Fix the assistant's irreversible send.** `AiAssistant.tsx` "Approve & send" gains preview-before-send, copy, and the personal-WhatsApp path; subject stops being hardcoded.

**2.5 Compose deeplink.** Add `?compose=whatsapp&text=…` on the lead route so compose jumps survive a page load or a deep link. Today they're in-page `CustomEvent`s only — invisible to mobile.

**2.6 Surface `stale` / `pending` / `cached`.** `RecapResult` returns all three; `LeadAiRecap.tsx` ignores all three. The mobile route already uses them.

## Phase 3 — Proactive (free, deduped)

**3.1 AI narrative in the daily summary.** Input is counts only — tiny prompt, one call per org per day, already gated by `isActionable()` and claimed via the `dailySummarySentOn` conditional-UPDATE. Cheapest high-perceived-value win in the whole spec, reusing an idempotency primitive that already exists.

**3.2 AI urgency alerts.** New worker modelled on `followUpReminderWorker.ts`: conditional-UPDATE claim + bounded lookback so downtime can't flood. Fires only when urgency is `now` **and** confidence is `high` **and** the rule NBA independently agrees it's high priority. Requires extending the three literal maps — `EMAIL_TYPES` in `notifications/service.ts`, `pushChannelFor` in `lib/push/channels.ts`, and i18n keys.

**3.3 AI ranking on `PriorityActions`.** Order "today's priorities" by AI confidence instead of the hand-rolled two-key comparator. Uses `cachedOnly: true` so it reads prewarmed recaps and never generates or spends.
